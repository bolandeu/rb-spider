# AGENTS.md

`rb-spider` — SEO-краулер для технического аудита, аналог Screaming Frog SEO Spider. Python-библиотека `rb_spider` + CLI `spider`, рассчитанный и на человека, и на ИИ-агентов.

## Статус

Этап: **волны MVP (178/178) и v2 (192/192, #26–#41) закрыты.** Обход до 100k URL (~1600–1700 URL/с, ~435 МБ, база ~540 МБ; проверки ~42 с), 171 проверка (MVP + URL, Hreflang, Pagination, Security, Content, Structured Data, Sitemaps, SERP, Validation, Mobile, JavaScript, Images v2), JS-рендеринг с `render = auto` и сравнением исходного HTML с отрендеренным, отчёты (`report …`, `redirects`, `hreflang`, `pagination`, `insecure`, `duplicates`, `structured`, `sitemaps show`, `custom`), `compare`, `crawls respider`, `robots-test`, xlsx и пресеты, `sitemaps build`, SERP в пикселях, PostgreSQL (`SPIDER_DB_URL`, extra `postgres`), extras `near` / `structured` / `sitemaps` (rb-sitemap-xml — путь `../sitemap-xml`) / `xpath`, режим списка, overview/export/query, обогатители, `spider fetch`, скилл и рецепты.
Следующий шаг — волна v3: задач с меткой `v3` в Issues ещё нет, их нарезает пользователь. Сделаны без задач пункты, которым не нужны внешние API: Link Score (`thresholds.link_score`) и скриншоты (`crawl.render_screenshots`). Остальное — PageSpeed/Lighthouse, Search Console, Majestic/Ahrefs (ключи API), визуализации, мобильные проверки уровня Lighthouse, а URL Mapping и staging vs production — «не подтверждено». Не измерено: скорость 100k после #39–#41 — бенч без присмотра не шёл (Mac с закрытой крышкой уходит в тепловой сон); память и база в норме. Бенч: `scripts/check.sh` + стенд 100k через `bench/measure.py` (~1700 URL/с, ≤ 500 МБ; во время бенча не читать его базу и не гонять тесты; верить `wall_s`). Разбор HTML — узкое место обхода; модули процессов разбора (`scope` → `extract`, `content`, `structured`) не импортируют SQLAlchemy, pydantic, Crawlee, numpy — это проверяет тест. Новые миграции должны работать и на SQLite, и на PostgreSQL (`scripts/check.sh --pg`).
Этот блок заменяется на месте при смене этапа; история — в git и CHANGELOG.

## Разработка

```bash
uv sync                                   # пишет uv.lock — он коммитится (CI: `uv lock --check`)
uv run spider                             # список команд; `uv run spider <команда> --help`
uv run ruff check . && uv run ruff format --check . && uv run ty check && uv run pytest
SPIDER_UPDATE_SNAPSHOTS=1 uv run pytest   # после намеренной правки справки или настроек: снимки --help и таблица docs/profiles.md
scripts/check.sh [--py312] [--linux] [--pg] # всё, что гоняет CI (хук pre-push); --linux — ещё и в Docker, релиз его требует; --pg — тесты на PostgreSQL
scripts/install_hooks.sh                  # один раз после клонирования: commit-msg и pre-push
```

Строка проверок — ровно то, что гоняет CI (Linux/macOS; Windows не поддерживается) перед `uv tool install .`. GitHub Actions сейчас не запускаются — проверяет `scripts/check.sh`. Пакет `rb-spider` (модуль `rb_spider`), команда и каталог проекта — `spider` / `.spider/` (`core/version.py`: `CLI_NAME`, `DIST_NAME`). `bench/` — отдельный uv-проект стенда, в пакет не входит.

Слои (архитектура `cli-builder`): `commands/` — только разбор аргументов → вызов сервиса → `output.emit_success`; логика — `core/`; внешние сервисы — `providers/`; секреты — `credentials/` (keychain + env `SPIDER_<PROVIDER>_<FIELD>`), никогда в `.spider/config.toml`. Группы команд — `output.group(...)`, каждая команда — под `@output.guard`, необратимые — `--dry-run` + `output.require_confirmation`.

Релиз: `uv run scripts/release.py patch|minor|major` из чистого `main` (версия, дата в CHANGELOG, тег, push — push делает пользователь). `version =` руками не менять.

## Документы

- `docs/spec.md` — **решения**: стек, модель данных, CLI, конфиг, интеграции, тесты. Прочитать перед любым архитектурным выбором; решение, которое расходится со spec, сначала согласовать с пользователем, затем обновить spec в том же коммите.
- **Задачи** — GitHub Issues `bolandeu/spider` (метки `mvp`, `ready-for-agent`), зависимости — нативная связь «blocked by». Брать задачу, у которой все блокеры закрыты.
- `docs/features.md` — **чеклист** функций по волнам (`MVP` / `v2` / `v3` / `backlog` / `skip`). Брать задачи из текущей волны; готовый пункт отмечать `[x]` в том же коммите, что и код.
- `docs/reference/screaming-frog.md` — исходный справочник SF (определения проверок, настройки, колонки). Открывать, когда реализуешь конкретную проверку или настройку.

## Правила

- **Архитектура CLI** — по скиллу `cli-generator:cli-builder` (Typer, dual human/`--json` вывод, ошибки с `code`/`message`/`action`, фиксированные exit-коды, `doctor`, конфиг проекта, секреты в keychain). Образец реализации — соседний `../sitemap-xml`.
- **Движок — Crawlee for Python.** Crawlee только обходит; извлечение SEO-данных — наш код на selectolax, одинаковый для сырого и отрендеренного HTML. Crawlee-хранилище за своим интерфейсом.
- **Память не растёт с размером сайта**: данные страниц и ссылок пишутся в БД пакетами, сайтовые проверки считаются SQL после обхода. Любая новая фича проходит этот тест.
- **Каждый параметр обхода — ключ конфига.** Новая настройка добавляется в pydantic-модель, автоматически доступна через профиль и `--set`; отдельный флаг — только для частых. Справочник ключей в `docs/profiles.md` генерируется из схемы.
- **Каждая проверка — страница-ловушка на полигоне** (aiohttp-сервер в pytest) и тест, что проверка её находит. Тесты работают только с полигоном; живые сайты — вручную, адреса даёт пользователь.
- **Соседние пакеты** — отдельные репозитории: sitemap (разбор и генерация) дорабатывается в `../sitemap-xml`, данные GSC / Яндекс Вебмастера приходят через плагины-обогатители на основе `../google-search-console`, `../yandex-webmaster`.
- **Постоянный стенд `https://spider.bolandau.ru`** — 20k страниц из `bench/bench_site.py build --pages 20000` (seed 42), для ручных и сетевых тестов краулера. Обходить можно свободно, параллельность ≤ 20: сервер одноядерный и общий с клиентскими сайтами. Передеплой (`hostme`) и удаление — только после подтверждения пользователя; на VPS ~3 ГБ свободно, стенд больше ~20k страниц не влезет.
- **Большие бенчи — локально**: `bench_site.py serve` отдаёт страницы на лету, ничего не пишет на диск. Результаты и сборки — во временную папку, не в репозиторий.

## Документация команд

Docstring команды и `help=` её опций — **единственный источник правды** о команде. Typer показывает их в `--help`, и это **основная документация и для человека, и для агента**: отдельного руководства по командам нет. Всё остальное генерируется из кода, а не пишется руками:

| Документ | Источник |
| --- | --- |
| `--help` каждой команды | docstring функции + `help=` опций |
| Список команд | голый `spider` (первая строка каждого docstring); в `data/SKILL.md` и README команд **нет** — там только соглашения, иначе они устареют |
| `docs/profiles.md` (справочник ключей) | генерируется из pydantic-схемы конфига (`description=` полей) |

Изменил поведение, флаг, значение по умолчанию, exit-код или формат вывода — в **том же коммите** обнови docstring / `help=` / `description=` и перегенерируй документы.

Docstring команды пишется по-русски, понятно новичку, и содержит по порядку:

1. **Первая строка** — что делает команда (её видно в списке `spider --help`).
2. **Когда использовать** и чем отличается от соседних команд.
3. **Примеры** вызова — 2–3 типичных.
4. **Выход**: что печатается человеку и форма `--json` (ключи верхнего уровня).
5. **Коды выхода**, если у команды есть свои, помимо общих.

`help=` опции — одна фраза: что задаёт, единицы и значение по умолчанию, ключ конфига, который она переопределяет. Рассказ о реализации — в комментариях к коду, не в docstring.

Гарантии:

| Проверка | Когда | Что ловит |
| --- | --- | --- |
| Хук `commit-msg` | каждый коммит `feat` / `fix` — блокирует | у команды изменились опции или логика, а docstring нет; у команды нет docstring |
| Тесты | перед каждым коммитом (коммитим только зелёное) | нет docstring / `help=` / `description=`; сгенерированные документы разошлись с кодом (генератор с `--check`); снимки `--help` каждой команды — любое изменение текста видно в diff |

`refactor` и `perf` по определению не меняют поведение, поэтому хук их пропускает. Если такой коммит на деле меняет поведение — это `feat` или `fix`, а не повод обойти проверку.

## Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/): `тип(область): что сделано`, заголовок по-русски, до 72 символов, без точки в конце. Проверяется хуком `commit-msg`.

| Тип | Когда |
| --- | --- |
| `feat` | новая возможность (пункт из `features.md`) |
| `fix` | исправление ошибки |
| `perf` | ускорение или снижение памяти без смены поведения |
| `refactor` | перестройка кода без смены поведения |
| `test` | только тесты / полигон |
| `docs` | только документация |
| `build` | зависимости, `pyproject.toml`, CI |
| `chore` | прочее обслуживание (скрипты, хуки) |

Области: `crawl`, `extract`, `issues`, `storage`, `config`, `cli`, `export`, `render`, `enrich`, `bench`, `polygon`. `!` после типа/области (`feat(cli)!:`) — ломающее изменение CLI, конфига или схемы БД.

- **Один коммит — одно логическое изменение**, законченное целиком: код + тесты + документация команд + отметка `[x]` в `features.md` + запись в `CHANGELOG.md` (секция `Unreleased`, формат Keep a Changelog) для `feat`/`fix`/`perf` и ломающих изменений.
- **Коммитим только зелёное**: `uv run pytest`, `uv run ruff check`, `uv run ty check` проходят.
- Тело коммита — **зачем** изменение, если это не очевидно из заголовка; что изменилось, видно в diff.
- После клонирования — `scripts/install_hooks.sh` (git не версионирует `.git/hooks/`).
