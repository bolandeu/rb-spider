# AGENTS.md

`rb-spider` — SEO-краулер для технического аудита, аналог Screaming Frog SEO Spider. Python-библиотека `rb_spider` + CLI `spider`, рассчитанный и на человека, и на ИИ-агентов.

## Статус

Этап: **волны MVP (178/178) и v2 (192/192, #26–#41) закрыты.** Обход до 100k URL (~1600–1700 URL/с, ~435 МБ, база ~540 МБ; проверки ~42 с), 171 проверка (MVP + URL, Hreflang, Pagination, Security, Content, Structured Data, Sitemaps, SERP, Validation, Mobile, JavaScript, Images v2), JS-рендеринг с `render = auto` и сравнением исходного HTML с отрендеренным, отчёты (`report …`, `redirects`, `hreflang`, `pagination`, `insecure`, `duplicates`, `structured`, `sitemaps show`, `custom`), `compare`, `crawls respider`, `robots-test`, xlsx и пресеты, `sitemaps build`, SERP в пикселях, общий PostgreSQL на homeserver (`SPIDER_DATABASE_URL`, таблицы `spider_*`, миграции — `spider db upgrade`; Mac — только SQLite), extras `near` / `structured` / `sitemaps` (rb-sitemap-xml по тегу) / `xpath` / `gsc`, режим списка, overview/export/query, обогатители, `spider fetch`, скилл и рецепты.
Волна v3 идёт: сделаны `spider lighthouse` (#44; источники local и PSI — #42, проверки PageSpeed / Mobile — #43), View Source и скриншоты (#51), URL Mapping в `compare` (#53), Link Score. Открыты интеграции #45–#47, #49, #52 (Search Console, Вебмастер, режим API без обхода, GA4) — только по запросу пользователя, через соседние пакеты (`gsc` — по тегу, extra `gsc`; `ywm`), ключи у них, тесты — на их фейковых клиентах; #48 и #50 — `backlog`. Не измерено: скорость 100k после #39–#41 (Mac с закрытой крышкой уходит в тепловой сон — `caffeinate -i`); память и база в норме. Бенч: `scripts/check.sh` + стенд 100k через `bench/measure.py` (~1700 URL/с, ≤ 500 МБ; во время бенча не читать его базу и не гонять тесты; верить `wall_s`). Разбор HTML — узкое место обхода; модули процессов разбора (`scope` → `extract`, `content`, `structured`) не импортируют SQLAlchemy, pydantic, Crawlee, numpy — это проверяет тест. Новые миграции должны работать и на SQLite, и на PostgreSQL (`scripts/check.sh --pg`).
Этот блок заменяется на месте при смене этапа; история — в git и CHANGELOG.

## Разработка

```bash
uv sync                                   # пишет uv.lock — он коммитится (гейт: `uv lock --check`)
uv run spider                             # список команд; `uv run spider <команда> --help`
uv run scripts/release.py --check         # гейт целиком — перед каждым коммитом (и хук pre-push)
uv run pytest --snapshot-update           # после намеренной правки справки: снимки tests/snapshots/help/ и describe.json
SPIDER_UPDATE_SNAPSHOTS=1 uv run pytest   # после правки настроек: таблица docs/profiles.md
scripts/check.sh [--py312] [--linux] [--pg] # тесты со всеми extras; --py312 — на Python 3.12, --linux — в Docker, --pg — на PostgreSQL (через scripts/pg_test.sh)
scripts/install_hooks.sh                  # один раз после клонирования: git-хуки из .githooks/ (сессии Claude Code — сами)
```

**Перед каждым коммитом `uv run scripts/release.py --check` проходит** — это главный гейт (tools/docs/standard-release.md §3): `uv lock --check`, ruff, ty, pytest (покрытие, контракт и снимки справки, форма `auth status`), список существующих тестов, изменённых или удалённых с последнего тега (`existing tests` — каждый в отчёт с причиной), фрагмент changelog, сборка wheel и установка в одноразовое окружение (`spider --version` = версия сборки), osv-scanner. Упавший шаг назван с выводом — чинить причину, не пропускать шаг. Гейт ставит все extras сам (`gate_extras` в `pyproject.toml`); `scripts/check.sh` — дополнительно другие окружения (3.12, Linux, PostgreSQL). Windows не поддерживается; GitHub CI нет: зависимости — приватные репозитории (standard-release.md §9). Пакет `rb-spider` (модуль `rb_spider`), команда и каталог проекта — `spider` / `.spider/` (`core/version.py`: `CLI_NAME`, `DIST_NAME`). `bench/` — отдельный uv-проект стенда, в пакет не входит.

**TDD обязателен и проверяется** (пользователь, 2026-10-02; `~/Work/dev/docs/testing.md`):

1. **Сначала красный.** Тест коммитится раньше кода, который его проводит, — порядок виден в git. Вывод падающего прогона сохранить: он идёт в отчёт о готовности.
2. **Тест не подгоняется под код.** Существующий тест меняется, только если изменилось требование. Шаг гейта `existing tests` перечисляет тесты прошлого релиза, которые изменены или удалены; каждый — в отчёт с причиной, без неё dev релиз не пропустит.
3. **Планку ставят другие.** Приёмочные сценарии пишет dev с пользователем, контрактные (`--json`, коды выхода, представления `v1`) — потребитель. Здесь пишутся модульные тесты и проходятся все чужие; контрактный тест потребителя — такой же существующий тест.
4. **Мутационное тестирование** — время от времени и перед крупным релизом (не в гейте): `uv run --group mutation mutmut run`, затем `mutmut results` / `mutmut browse`; выживший мутант — строка, которую ни один тест по-настоящему не проверяет. spider большой — по модулю (`only_mutate` в `[tool.mutmut]`).

Отчёт о готовности (`~/Work/tools/scripts/agent_say.sh tools "…"`): что внутри, красный прогон, изменённые существующие тесты с причинами, итог гейта.

**Команда дольше пары минут** (гейт, `pytest`, `scripts/pg_test.sh`, бенч, долгий `spider`) — только отвязанно: `scripts/run_detached.sh <метка> <команда…>`, статус — `scripts/runs_status.sh <метка>` (`--json` — код выхода и хвосты вывода), остановить — `python3 scripts/detach.py stop <метка>`. В своём shell агента команда умирает при прерывании хода (входящее сообщение herdr — тоже прерывание).

**База** — через `core/db.py` (cli-generator `architecture.md` §12). `SPIDER_DATABASE_URL` → общий PostgreSQL (прод, homeserver), иначе локальная SQLite (`SPIDER_DB_PATH` — другой файл; Mac работает только на ней). Таблицы, представления, индексы — только `spider_*`, объявлены в `core/tables.py`, создаются миграцией, написанной руками; функций и агрегатов в `public` spider не создаёт, кроме `spider_*`. Другие инструменты и Directus читают только представления `spider_v1_*` (новая форма — `_v2_` + строка в Service map); каждое объявлено в `tables.views` (колонки с типами и `comment=`) — `spider describe --json` публикует их как контракт данных (OpenCLI, `x-rb-data`), тест сверяет с мигрированной базой. У каждой таблицы `info={"kind": "data" | "cache"}`; файлы в user data dir помимо базы — `core/data_files.py`. У каждой таблицы PRIMARY KEY из одной колонки (суррогатный `id`; составной Directus не поддерживает), естественный ключ — UNIQUE. SQLite мигрирует при открытии; общую базу — только `spider db upgrade` из релиза; каждая миграция совместима с предыдущим релизом (expand/contract). PostgreSQL в тестах — только `scripts/pg_test.sh` (свой контейнер, порт от Docker). Миграции 0001–0032 — только SQLite: новая PostgreSQL получает базовую схему 0033 из `migrations/pg_baseline.py` и дальше идёт по цепочке.

Слои (архитектура `cli-builder`): `commands/` — только разбор аргументов → вызов сервиса → `output.emit_success`; логика — `core/`; внешние сервисы — `providers/`; секреты — `credentials/` (keychain-сервис `spider:<provider>` + env `SPIDER_<PROVIDER>_<FIELD>`; `auth status` — отчёт по §8), никогда в `.spider/config.toml`. Группы команд — `output.group(...)`, каждая команда — под `@output.guard`, необратимые — `--dry-run` + `output.require_confirmation`.

Версия — **git-тег** `vX.Y.Z` (uv-dynamic-versioning), строки `version =` в `pyproject.toml` нет и не будет. Релиз: `uv run scripts/release.py patch|minor|major` из чистого `main` — гейт, сборка CHANGELOG из фрагментов, коммит `Release vX.Y.Z`, тег; **никто здесь не пушит**: готовый релиз или ветку — корневому агенту `tools` (`~/Work/tools/scripts/agent_say.sh tools "<репозиторий, ветка, теги, что внутри, итог release.py --check>"`, одно сообщение на тег); он проверяет и ставит в очередь dev, dev показывает пользователю и после «да» пушит, затем `tools` ставит релиз на Mac и homeserver. Вопросы пользователю — тем же каналом. **В прод ходит только `tools`**: никаких команд против прода — ни `db push`, ни `--dry-run`, ни чтения через `*_PROD_DATABASE_URL`, ни ssh на homeserver; нужна проверка на проде — прислать `tools` точную команду, он выполнит и вернёт вывод. Локальная временная база (`scripts/pg_test.sh`) — своя. **Ничего в обход `tools`**: задачи ставит он; другим агентам (инструменты, sysadmin, dev, windmill…) указаний не давать, вне этого репозитория ничего не менять; баг или просьба к другому инструменту или инфраструктуре — сообщением `tools` (`~/Work/tools/scripts/agent_say.sh tools "…"`), он решит и передаст. SemVer: пока `0.x`, исправление или совместимая функция — patch, ломающее изменение (команды, флаги, форма `--json`, коды выхода и ошибок) — minor. Соседние пакеты — только по тегу в `[tool.uv.sources]` с диапазоном в зависимостях (`>=0.1,<0.2`), никогда `path =` или `branch`; работа с невыпущенным соседом — `uv pip install -e ../<пакет>`, без коммита.

## Правила

- **Архитектура CLI** — по скиллу `cli-generator:cli-builder` (Typer, dual human/`--json` вывод, ошибки с `code`/`message`/`action`, фиксированные exit-коды, `doctor`, конфиг проекта, секреты в keychain). Образец реализации — соседний `../sitemap-xml`.
- **Движок — Crawlee for Python.** Crawlee только обходит; извлечение SEO-данных — наш код на selectolax, одинаковый для сырого и отрендеренного HTML. Crawlee-хранилище за своим интерфейсом.
- **Память не растёт с размером сайта**: данные страниц и ссылок пишутся в БД пакетами, сайтовые проверки считаются SQL после обхода. Любая новая фича проходит этот тест.
- **Каждый параметр обхода — ключ конфига.** Новая настройка добавляется в pydantic-модель, автоматически доступна через профиль и `--set`; отдельный флаг — только для частых. Справочник ключей в `docs/profiles.md` генерируется из схемы.
- **Каждая проверка — страница-ловушка на полигоне** (aiohttp-сервер в pytest) и тест, что проверка её находит. Тесты работают только с полигоном; живые сайты — вручную, адреса даёт пользователь.
- **Соседние пакеты** — отдельные репозитории: sitemap (разбор и генерация) дорабатывается в `../sitemap-xml`, данные GSC / PageSpeed / GA4 / Яндекс Вебмастера — через обогатители в spider (extras), которые вызывают библиотеки `../google-search-console` (пакет `gsc`), отдельного инструмента GA4 (пока нет) и `../yandex-webmaster` (`ywm`); ключи и авторизация — у этих инструментов, spider их не хранит. Интеграции — только по запросу пользователя.
- **Постоянный стенд `https://spider.bolandau.ru`** — 20k страниц из `bench/bench_site.py build --pages 20000` (seed 42), для ручных и сетевых тестов краулера. Обходить можно свободно, параллельность ≤ 20: сервер одноядерный и общий с клиентскими сайтами. Передеплой (`hostme`) и удаление — только после подтверждения пользователя; на VPS ~3 ГБ свободно, стенд больше ~20k страниц не влезет.
- **Большие бенчи — локально**: `bench_site.py serve` отдаёт страницы на лету, ничего не пишет на диск. Результаты и сборки — во временную папку, не в репозиторий.

## Документация команд

Docstring команды и `help=` её опций — **единственный источник правды** о команде. Typer показывает их в `--help`, и это **основная документация и для человека, и для агента**: отдельного руководства по командам нет. Всё остальное генерируется из кода, а не пишется руками:

| Документ | Источник |
| --- | --- |
| `--help` каждой команды | docstring функции + `help=` опций |
| Список команд | голый `spider` (первая строка каждого docstring); в `data/SKILL.md` и README команд **нет** — там только соглашения, иначе они устареют |
| `docs/profiles.md` (справочник ключей) | генерируется из pydantic-схемы конфига (`description=` полей) |

Изменил поведение, флаг, значение по умолчанию, exit-код или формат вывода — в **том же коммите** обнови docstring / `help=` / `description=` и перегенерируй документы.

Docstring команды пишется по-русски, понятно новичку, и содержит по порядку:

1. **Первая строка** — что делает команда (её видно в списке `spider --help`).
2. **Когда использовать** и чем отличается от соседних команд.
3. **Примеры** вызова — 2–3 типичных, каждый строкой `Example: {cli} <команда> …` (`{cli}` превращается в `spider`; строку ищет контракт-тест).
4. **Выход**: что печатается человеку и форма `--json` (ключи верхнего уровня).
5. **Коды выхода**, если у команды есть свои, помимо общих.

`help=` опции — одна фраза: что задаёт, единицы и значение по умолчанию, ключ конфига, который она переопределяет. Рассказ о реализации — в комментариях к коду, не в docstring.

Гарантии:

| Проверка | Когда | Что ловит |
| --- | --- | --- |
| Хуки Claude Code (`.claude/settings.json`) | после правки файла команды и перед концом хода | у команды изменились опции или логика, а docstring нет |
| Хук `pre-commit` (`.githooks/`) | каждый коммит — блокирует | то же по staged-файлам; ещё предупреждает, если `src/` менялся без фрагмента changelog |
| Тесты (`tests/test_help.py`) | в гейте | нет docstring со строкой `Example:`, `help=`, описания группы; снимки `--help` каждой команды и группы — любое изменение текста видно в diff; сгенерированные документы разошлись с кодом |

Если хук сработал на правку, которая правда не меняет поведение (`refactor`, `perf`), — `SKIP_DOCSTRING_CHECK=1 git commit …` и сказать об этом, а не обходить молча.

## Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/): `тип(область): что сделано`, заголовок по-русски, до 72 символов, без точки в конце. Проверяется хуком `commit-msg`; релизный `Release vX.Y.Z` от `release.py` пропускается.

| Тип | Когда |
| --- | --- |
| `feat` | новая возможность (пункт из `features.md`) |
| `fix` | исправление ошибки |
| `perf` | ускорение или снижение памяти без смены поведения |
| `refactor` | перестройка кода без смены поведения |
| `test` | только тесты / полигон |
| `docs` | только документация |
| `build` | зависимости, `pyproject.toml`, CI |
| `chore` | прочее обслуживание (скрипты, хуки) |

Области: `crawl`, `extract`, `issues`, `storage`, `config`, `cli`, `export`, `render`, `enrich`, `bench`, `polygon`. `!` после типа/области (`feat(cli)!:`) — ломающее изменение CLI, конфига или схемы БД.

- **Один коммит — одно логическое изменение**, законченное целиком: код + тесты + документация команд + отметка `[x]` в `features.md` + фрагмент changelog для `feat`/`fix`/`perf` и ломающих изменений: `uv run towncrier create +<slug>.<type>.md -c "…"` (тип — added/changed/deprecated/removed/fixed/security, в slug без точек). `CHANGELOG.md` руками не правится — его собирает `release.py`.
- **Коммитим только зелёное**: `uv run scripts/release.py --check` проходит.
- Тело коммита — **зачем** изменение, если это не очевидно из заголовка; что изменилось, видно в diff.
- После клонирования — `scripts/install_hooks.sh` (включает версионируемые хуки `.githooks/`).

## Каждое заметное изменение выходит релизом

Серверы, другие инструменты и Mac ставят только по тегам, не из `main`:
влитое без релиза изменение для них не существует. Изменение с фрагментом
changelog закончено только после релиза: влить в `main` →
`uv run scripts/release.py patch|minor|major` → сообщить `tools`
(push делает dev после «да» пользователя) → назвать новый тег в отчёте. Служебные коммиты
(без фрагмента) ждут следующего релиза. Не оставлять фрагмент на `main` без
релиза, не назвав причину (`~/Work/tools/docs/standard-release.md` §3).

## Инструмент в системе

Инструмент — один из сервисов `~/Work/tools/`: корневой агент его
деплоит, хранит ключи (Doppler) и бэкапит данные (S3). Полные правила —
`~/Work/tools/docs/standard-release.md` §13.

- **Сообщать корневому агенту** (в отчёте пользователю, рядом с тегом
  релиза): новая или переименованная переменная окружения / ключ, новая
  локальная база или новый путь к данным, новая или убранная зависимость от
  другого инструмента, обновлённый токен сохраняется локально, ломающий релиз.
- **Потребители**: перед ломающим изменением проверить, кто пользуется
  инструментом (корневой `AGENTS.md` → Service map), и назвать их в отчёте.
- **Серверы Linux без экрана**: сначала переменные окружения, keychain
  необязателен (его отсутствие при заданной переменной — не ошибка); имена
  переменных — уже существующие; без TTY никаких вопросов; без путей только для Mac.
- **Локальные данные** — в `platformdirs.user_data_dir("<tool>")`, не в
  репозитории; всё состояние — в файле базы, миграции делает сам инструмент;
  сам инструмент данные никуда не выгружает.
